# SOLUTION

## Что сделано и какие решения приняты

### Скидки в `GET /customers/:id/daily-totals`

Ответ по каждому дню: `date`, `total`, `gross`, `discount`, `net`.

- `gross` / `total` — сумма `amount` оплаченных заказов (до скидки).
- `net` — сумма `amountPaid` (сколько заплатили).
- `discount` — `gross - net`, считается в копейках и переводится в рубли.

Деньги по-прежнему хранятся в копейках. В таблицу `orders` добавлена колонка `amount_paid_kop`.

**Миграция мягкая:** только `ADD COLUMN … BIGINT` без `UPDATE` и без `SET NOT NULL`. Полный бэкфилл на большой таблице повесил бы лок. Старые строки остаются `NULL`; при чтении `NULL` трактуется как `amount_kop` (скидки ещё не было). Новые и обновлённые заказы пишут `amount_paid_kop` при sync/webhook.  

При желании добавить отдельным скриптом backfill, аля:

```sql
UPDATE orders
SET amount_paid_kop = amount_kop
WHERE id IN (
  SELECT id FROM orders
  WHERE amount_paid_kop IS NULL
  LIMIT 1000
);
```

`discountPercent` в статистику не идёт: net берётся из `amountPaid`, как **фактическая** оплата.

### Жалоба по дням

Календарный день заказа считается в IANA-зоне клиента **на момент** `createdAt`, а не одним смещением на весь диапазон. Для этого добавлен `calendarDateInZone` (`tzOffsetMinutes(timeZone, at)` + `dateAtOffset`).

## Причина расхождения

Формулировка «конец марта, **часть** дней не сходится, остальные — до копейки» не похожа на ошибку сумм или скидок: те дали бы сдвиг на всех днях. Сперва подумал на стык месяцев, но апрель не цепляется.

В `TotalsService.daily` смещение зоны бралось один раз:

```ts
const offset = tzOffsetMinutes(timezone, new Date());
```

и этим числом сдвигались все заказы. `new Date()` — момент **запроса**, а не заказа. В ЕС последнее воскресенье марта — перевод на летнее время (в 2026 это **29 марта**, CET +1 → CEST +2). Диапазон 27–31.03 как раз под этот стык.

Пример: `Europe/Berlin`, `2026-03-29T22:30:00Z`.

- правильный CEST (+2) → 30.03 00:30 → **30.03**;
- зимний +1 (если считать «как сейчас» в ноябре) → 29.03 23:30 → **29.03**.

В неправильный день попадают только заказы у полуночи. Остальные дни совпадают до копейки. Плюс результат зависел от сезона, в котором дернули API.

Исправление: для каждого заказа `calendarDateInZone(o.createdAt, timezone)`.

## Что ещё замечено

- Внешний API: лимит 5 rps, 429 без `Retry-After`, иногда 200 с `{ "error": "rate_limited" }` — клиент это уже обрабатывает.
- Даты без суффикса зоны (`2026-03-01T00:40:39`) считаются UTC — это уже есть в `parseUtc`.
- Таймзона клиента кэшируется в БД при первом запросе и больше не обновляется.
- `OrdersApi.getCustomer` в HTTP-клиенте не проверяет `id` в теле, подставляет id из URL.
- Окно выборки заказов по-прежнему ±сутки вокруг UTC-полуночи; для DST этого запаса достаточно (±14 ч).

## Из отмеченных моментов

- Нет `amountPaid` → net = gross (старые заказы / неполный payload).
- `discount` не пересчитывается из процента: источник истины — `amountPaid`. Если процент и оплата расходятся, верим оплате.
- Невалидный `discountPercent` заказ не ломает: поле игнорируется.
- `amountPaid` = 0 — валидная 100% скидка, поэтому колонку нельзя было «просто задефолтить в 0» и отличить от «ещё не заполнена».
- В статистику по-прежнему входят только `status = paid`.
- День — локальная календарная дата `createdAt`, не `updatedAt` и не момент оплаты (его в API нет).
